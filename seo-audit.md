# SEO Audit — Las Vegas Warehouse

**Scope note:** the audit brief this was run from was written for a prerendered Vite/React SPA with a build pipeline (`dist/`, per-route prerendering, code-splitting). This repository is a different kind of project — a hand-authored static site: 14 flat `.html` pages, one shared `css/style.css`, one shared `js/main.js`, no framework, no build step. The categories below are the same ten from that brief, adapted to what actually exists here. Category 1 (confirm SSG prerendering) is reinterpreted accordingly — see below. Fixes were made directly in source (the files a browser/crawler actually receives — there is no separate build output to go stale).

All fixes were verified with a local static server + a headless-browser crawl of all 15 pages (14 content pages + the new `404.html`) after every batch of changes: zero broken assets, zero console errors, exactly one `<h1>` per page.

## 2. Heading structure — 98

**What's already right:** every one of the 14 pages (now 15 with `404.html`) has exactly one `<h1>`, and every `<h1>` is unique and matches the page's actual topic (not a repeated "Las Vegas Warehouse" site-name pattern) — e.g. `index.html` H1 is "Exceptional Warehouse Storage Services.", `cross-docking.html` H1 is "Cross Docking Warehouse Storage Service". This was already true before this audit.

**P1 — Fixed.** `index.html:99` (pre-fix) had an `<h3>` ("We're Proud Of Our Clients!") with no `<h2>` anywhere earlier on the page — a level skip (H1 → H3). Every other section on the page uses `<h2>` for the same structural role. Changed to `<h2>`:
```diff
- <h3 class="center" style="margin-bottom:var(--space-6);">We're Proud Of Our <span class="accent">Clients</span>!</h3>
+ <h2 class="center" style="margin-bottom:var(--space-6);">We're Proud Of Our <span class="accent">Clients</span>!</h2>
```

**No other issues found.** `privacy-policy.html:167,187` has two `<h3>`s ("Personal Information Disclosures", "Sensitive Personal Information Disclosures") both correctly nested under an `<h2>` — no skip. No heading anywhere is used purely for visual size instead of structure — the site's decorative oversized watermark text (`.ghost-word`) is correctly implemented as plain `<div>`s, not headings.

2-point deduction is stylistic, not structural: card/feature titles across the site (`.card-title`, `.fb-title`, `.dc-title`, `.tl-title`, `.n-title` — dozens of instances) are `<div>`s, not headings. This is a defensible, common choice for grid-of-cards content (avoids heading soup), not a violation of "no heading skips," so it isn't scored as an error — noting it only because a stricter reading of "rich document outline" would want some of these promoted to `<h3>`/`<h4>` for screen-reader landmark navigation.

## 3. Meta tags — 98

**Before this audit: zero `<link rel="canonical">`, zero Open Graph tags, zero Twitter Card tags existed anywhere on the site.** This was the largest gap in this category.

**P0 — Fixed, all 14 pages.** Added a full block to every page's `<head>`: `canonical`, `og:type`, `og:site_name`, `og:title`, `og:description`, `og:url`, `og:image` (absolute URL, real photo — not a placeholder), `twitter:card` (`summary_large_image`), `twitter:title`, `twitter:description`, `twitter:image`. No leftover Lovable/template defaults existed to remove — this site was hand-built, not generated by a template builder.

**P0 — Fixed.** Canonical/OG URLs initially pointed to the `.html` filenames. Mid-audit, live testing (`curl -I`) showed Cloudflare Pages 308-redirects every `*.html` request to its extensionless form (`/warehouse-services.html` → `/warehouse-services`) — a platform behavior, not anything in this repo. A canonical tag pointing at a URL that immediately redirects away is a real indexing problem (Search Console flags "canonical URL is not indexable"). Re-pointed every canonical/`og:url`/sitemap entry to the actual final destination — see Category 6 for the full writeup.

**Judgment call worth flagging:** `warehouse-services.html`'s `og:image` deliberately does **not** use that page's own hero background (`images/warehouse-storage-services-hero.webp`) — that photo is a Ferrari Formula 1 car being crated, and you're mid-decision (asked in a prior session, not yet answered) on whether to remove F1-branded imagery from the site. Defaulting the *social-share preview image* to that exact photo would actively amplify it across Facebook/LinkedIn/X/iMessage previews while that's unresolved, so I used `images/storage-solutions.webp` instead. See the P1 note under Images below — this same photo (and a second one, `car-crating-storage.webp`) is still live elsewhere on the site.

**Title tags:** all 14 unique, all under 60 characters, all in the recommended `{Specific Topic} | Las Vegas Warehouse` order (keyword first) — already correct, no changes needed.

**Meta descriptions:** all now unique and under 155 characters. Three were over on inspection and trimmed:
- `index.html`: 164 → 149 chars
- `antiques-and-auctions.html`: 161 → 131 chars
- `fine-art-installation-removal.html`: 168 → 148 chars

**Viewport / lang:** already correct on every page (`<meta name="viewport" content="width=device-width, initial-scale=1.0">`, `<html lang="en">`) — no changes needed.

2-point deduction: none of this has been run through Google's actual Rich Results Test or a live Facebook/Twitter card debugger against the deployed domain — see "Could not verify" at the bottom.

## 5. Structured data (JSON-LD) — 80

**Before this audit: zero JSON-LD anywhere on the site.** This was the single biggest gap in the whole audit, and the brief is explicit that this is the section that matters most.

**P0 — Fixed, 13 of 14 indexable pages** (`thank-you.html` is `noindex` and intentionally excluded — a post-submission utility page has no SEO value to carry schema for). Built one connected `@graph` per page, using the *same* `@id` values everywhere so Google can recognize these as one entity across every page load rather than "disconnected schema islands":

- **`Organization`** (`#organization`) — name, url, logo, and `sameAs` linking to the *real* profiles that exist: X (`x.com/lasvwarehouse`), LinkedIn (`linkedin.com/company/101277738`), and the Google Maps listing linked from the homepage's review badge. Did **not** include Facebook — the footer's Facebook icon links to `href="#"` (a placeholder, not a real profile — see Category 7), so adding it to `sameAs` would have been exactly the "empty/placeholder" schema fabrication the brief warns against.
- **`WebSite`** (`#website`) — no `SearchAction`, correctly omitted: there is no on-site search feature anywhere in `js/main.js` or any page, so adding one speculatively would be fabricated.
- **`LocalBusiness`**, typed as `["SelfStorage", "MovingCompany"]` (`#localbusiness`) — the two most specific schema.org subtypes that actually match what this business does (storage + local moving/logistics), rather than a bare `LocalBusiness` fallback. NAP (name/address/phone) matches what's already consistently published across every page of the site itself: `4640 Polaris Ave, Las Vegas, NV 89103`, `+18008064119`. **I could not cross-check this against the live Google Business Profile** — see "Could not verify."
- **`Service`**, on the 7 pages that describe one distinct service (`warehouse-services.html`, `safe-secure-art-storage.html`, `antiques-and-auctions.html`, `convention-storage.html`, `cross-docking.html`, `fine-art-installation-removal.html`, `small-local-moves-and-storage.html`) — each references `provider: {"@id": ".../#localbusiness"}` rather than repeating flat business details.
- **`BreadcrumbList`**, on all 12 interior pages (everything except the homepage and `thank-you.html`), matching the *real*, honest nav hierarchy — see Category 6/7 for detail on why some are 2-level and one is 3-level.

**Correctly and deliberately omitted, not just skipped:**
- **`FAQPage`** — no page has visible, verbatim Q&A content anywhere on the site. Adding it would be exactly the "schema claiming content that isn't visible" the brief calls out as a manual-action risk.
- **`AggregateRating` / `Review`** — the homepage and `get-started.html` display 5 real named customer reviews, but the on-page star display (`js/main.js:387`, `starSVG().repeat(5)`) is a hardcoded 5 stars for *every* review — there is no real per-review rating value in the source data (`data-reviews` only carries `name`/`meta`/`quote`). I have no live GBP `ratingValue`/`reviewCount` to verify against either. Adding rating schema here would mean fabricating numbers — explicitly the thing the brief says is worse than no schema at all. Left out; flagged for you to add once you have real GBP numbers.
- **`HowTo`** — `cross-docking.html` has a genuine 4-step numbered explanation ("A Typical Cross-Docking Scenario"), but it's *describing* how the business's internal process works, not instructing the reader through a task they'd perform themselves. Applying `HowTo` here would be a stretch that risks failing Google's required-property checks for that type. Left as plain content.
- **`JobPosting`** — `careers.html` is a general "we're hiring, apply here" page with no specific job title, no `datePosted`, no `employmentType`, no actual open position listed. `JobPosting` has hard required properties none of this content backs. Left out.
- **`Product`** — no purchasable product with a price exists anywhere on a service-only site. Correctly never considered.

**Deductions (20 points):**
- Every block validates as syntactically correct JSON (verified with `json.loads` on all 13 blocks), but **none of this has been run through Google's actual Rich Results Test** — a block can be syntactically valid and still fail Google's required/recommended-property checks for that specific type. This genuinely could not be done from this environment. See "Could not verify."
- `LocalBusiness` NAP is sourced from the site's own consistently-published address/phone, not cross-checked against a live GBP listing, per the brief's own explicit example of a "common silent failure."
- No `AggregateRating`/`Review` schema at all, given the constraints above — a real gap in rich-result eligibility once you have verified numbers to add.

## 6. URL & routing structure — 88

**Clean URLs:** already good — every filename is lowercase, descriptive, hyphenated. No change needed.

**P0 — found and fixed: canonical/sitemap were pointing at self-redirecting URLs.** Mid-audit, live testing surfaced that Cloudflare Pages natively 308-redirects every `*.html` URL to its extensionless equivalent (confirmed live: `curl -I https://lasvegaswarehouse.com/warehouse-services.html` → `308` → `location: /warehouse-services` → `200`, and the extensionless URL serves the correct page content, verified by title match). This is a platform behavior, not something in `_redirects` or any file here — but the canonical tags this audit had just added (and `sitemap.xml`) initially declared the `.html` form as canonical, which is a URL that never actually gets indexed as-is (Google follows the redirect and indexes the destination). Fixed by re-pointing every canonical, `og:url`, `sitemap.xml` entry, and `BreadcrumbList` item URL to the actual final destination (e.g. `https://lasvegaswarehouse.com/warehouse-services`, no extension).

**P1 — found and fixed: a redundant double-redirect, and one backwards rule.** `_redirects` was sending legacy WordPress URLs (e.g. `/warehouse-services/`) to the `.html` form, which Cloudflare then redirected *again* to the extensionless form — two hops where one would do. Updated every rule to target the final destination directly. Separately, the `/thank-you → /thank-you.html` rule added when the thank-you page was built was actually backwards once Cloudflare's native behavior is accounted for — visiting `/thank-you` would have bounced to `/thank-you.html` and immediately back to `/thank-you`. Removed the rule entirely (unnecessary — Cloudflare's native handling already serves `thank-you.html`'s content at `/thank-you` directly) and changed the post-submit JS redirect in `js/main.js` (`THANK_YOU_PATH`) to navigate straight to `/thank-you`.

**P0 — Fixed: `robots.txt` didn't exist in this repo.** The live domain was serving Cloudflare's generic default (an "AI content signals" boilerplate file) with no reference to the sitemap. Added a real `robots.txt` at the repo root:
```
User-agent: *
Allow: /

Sitemap: https://lasvegaswarehouse.com/sitemap.xml
```
Doesn't block `/assets/`, `/css/`, or `/js/` (no `Disallow` rules at all beyond none). **Not verified live post-deploy** — see "Could not verify."

**P0 — Fixed: no real 404 handling.** Confirmed live before this fix: any nonexistent path (e.g. a typo'd URL) returned `200` with the *homepage's* content instead of a real 404 — a soft-404 that can quietly hurt crawl budget and indexing signals. Added `404.html` at the repo root (on-brand, `noindex`, links back to Home and key service pages) — Cloudflare Pages serves this file with an actual 404 status for any unmatched route when it exists at the repo root. **Not verified live post-deploy** — see "Could not verify."

**Deductions (12 points):**
- `sitemap.xml` is hand-maintained, not auto-generated from a route list at build time — there is no build step in this repository for it to be generated by. It currently *is* accurate (all 13 indexable pages present, `thank-you.html`/`404.html` correctly excluded as noindex/utility), but will silently go stale if a page is added or removed later without a matching manual edit. This is an inherent limitation of the site's architecture (no templating/build system), not something fixable without introducing one.
- Internal `<a href="...">` links throughout the site (nav, footer, in-page body links) still point to the `.html` filenames rather than the extensionless final destination. This means every internal navigation click still takes one redirect hop through Cloudflare's native `.html`-stripping before landing. This is a known inefficiency, left as-is deliberately: earlier in this project you explicitly chose to keep `.html` as the canonical link/file scheme rather than restructure the site into `slug/index.html` folders, and re-litigating that decision wasn't this audit's call to make unilaterally. Fixing it would mean rewriting every internal `href` across 14 files plus `js/main.js`'s nav/footer generation — flagging it here as a known, quantified follow-up rather than doing it silently.

## 8. Performance (code-level) — 90

**P1 — Fixed: Google Fonts loaded via a render-blocking `@import`.** `css/style.css` had `@import url('https://fonts.googleapis.com/css2?...')` at the top of the file — this serializes the load into CSS → parse → discover import → fetch font CSS → parse → discover font files, a chain of sequential round-trips before text can render in the intended typeface. Removed the `@import`; added `<link rel="preconnect">` (×2, for `fonts.googleapis.com` and `fonts.gstatic.com`) plus a direct `<link rel="stylesheet">` for the font CSS to every page's `<head>`, ahead of `css/style.css`, so the browser can start the font fetch in parallel with everything else instead of after. `font-display: swap` was already present in the Google Fonts query string (`&display=swap`) — that part didn't need fixing.

**Already good, no changes needed:**
- `gtag.js` loads `async` (`index.html:5` and identically on every page).
- `js/main.js` loads at the end of `<body>`, not in `<head>` — doesn't block initial render.
- The third-party feedbucket QA-feedback script is `defer`red *and* gated behind `window.location.hostname === 'las-vegas-warehouse.pages.dev'` — meaning it never even loads on the production custom domain (`lasvegaswarehouse.com`) at all. Zero production impact already.
- No other third-party scripts exist.

**Not applicable / structurally N/A:**
- "Code splitting / lazy loading of routes or components" — this is a multi-page static site, not an SPA with client-side routes; each page already loads only its own HTML, sharing one cached `css/style.css`/`js/main.js` across navigations. There's no route-splitting concept to apply here.

**Not fully verified:** "minimal unused CSS" — one shared ~40KB stylesheet across 15 pages will always carry some per-page-unused rules by nature of being shared; measuring actual per-page coverage requires a real Chrome DevTools Coverage-tool pass against the live site, which this environment can't run. File size itself isn't a red flag at this scale.

## 9. Accessibility & mobile — 85

**P1 — Fixed: no skip-to-content link.** Added `<a class="skip-link" href="#main-content">Skip to main content</a>` as the first element after `<body>` on all 15 pages, plus `id="main-content"` on every `<main>`. Styled off-screen until focused (`css/style.css`, new `.skip-link` rule) — standard, well-established pattern.

**P1 — Fixed: dropdown/mobile-menu toggles had no ARIA state.** Added `aria-haspopup="true"` + `aria-expanded` (kept in sync on click, in `wireDropdowns()`/`wireMobileNav()` in `js/main.js`) to both nav dropdown triggers, the mobile submenu toggles, and the hamburger menu button (`aria-controls="mobileNav"` added too). Verified live: clicking "What We Do" flips `aria-expanded` from `false` to `true`.

**P1 — Fixed: two real horizontal-scroll bugs on mobile**, found by measuring `document.documentElement.scrollWidth` against viewport width across all 15 pages at 375px and 320px:
- `get-started.html:147` used an ad-hoc inline `style="display:grid;grid-template-columns:1.1fr 0.9fr;..."` with no mobile breakpoint, unlike every other 2-column layout on the site (which use the shared `.split` class, which *does* have a `grid-template-columns: 1fr` mobile override at `css/style.css:705`). At 320px viewport this squeezed the contact form into a 116px page overflow. Fixed by switching to `class="split"` (keeping only the `align-items:start` override inline) — now inherits the same responsive behavior as every other split section on the site.
- `privacy-policy.html` had a 19px overflow at 320px, traced to one specific link (`https://www.facebook.com/business/help/742478679120153?id=...`) used as its own unbroken visible anchor text, among several similarly long raw URLs in that page's legal copy. Fixed with `overflow-wrap: break-word` on `.legal-body` (`css/style.css`) so long URLs wrap instead of forcing the page wider than the viewport.
- Verified: 0 overflow issues remain across all 15 pages at both 375px and 320px viewports after the fix (re-crawled with a headless browser).
- Note: the wide data tables further down `privacy-policy.html` were *not* part of this bug — they already scroll correctly inside their own `.legal-table-wrap { overflow-x: auto }` container without leaking into page-level scroll, which is the correct pattern per this brief's own guidance on wide tables.

**Already good, no changes needed:** `<main>` was already present on every page; `<section>` used extensively and correctly for grouped content. `<article>` isn't used anywhere, which is correct — nothing on this marketing/services site is a self-contained, independently-distributable piece of content (no blog posts, no reviews-as-content) that would call for it.

**P2 — found, not fixed:** the hamburger menu button (`js/main.js:109`, `.nav-toggle` in `css/style.css:285`) renders at 40×32px on mobile — above the WCAG 2.2 AA minimum (24×24px) but below the stricter AAA guideline (44×44px). Left as-is rather than risk a visual-design change to the header without you weighing in — a few extra pixels of padding would close the gap if you want it.

**Not fully automate-verified:** added `:focus-within` to `css/style.css` so the "Warehouse Services" dropdown (which is otherwise only mouse-hover-triggered, a pre-existing keyboard-accessibility gap) also opens on keyboard focus. This is standard, widely-supported CSS and passed in an isolated minimal-repro test in the same browser engine, but I could not get the specific interaction on the live page to register in this sandboxed headless-browser test environment — `element.matches(':focus-within')` correctly returned `true` after a programmatic `.focus()` call, but the sibling `.dropdown` element's `getComputedStyle` didn't reflect the matching rule within the same synchronous check, which looks like a style-invalidation quirk specific to CDP-driven focus calls rather than a real bug in the CSS (the rule is textbook-correct and doesn't touch the already-working hover/click paths). Worth a real-device/real-browser spot-check.

## What this audit could not verify

Everything below requires either live production access (the domain has since redeployed several times during this session, so "live" state may differ from what was tested) or external tools/APIs this environment doesn't have:

- **Google's Rich Results Test** was not run against any URL — all JSON-LD was validated as syntactically correct JSON and structurally checked against each type's documented required properties by hand, but only Google's own tool can confirm a block actually qualifies for rich results.
- **Live Google Business Profile data** — the `LocalBusiness` NAP (address/phone) is sourced from what's already consistently published across the site itself, not cross-checked against the live GBP listing. Review count/rating was deliberately *not* added rather than guessed.
- **`robots.txt` and `404.html` serving correctly in production** — both are new files; Cloudflare Pages should serve them directly once deployed (same mechanism that serves every other static file here), but this wasn't confirmed with a live `curl` post-deploy in this session.
- **Real Open Graph / Twitter Card previews** — not spot-checked with Facebook's Sharing Debugger or Twitter's Card Validator against the live domain.
- **Actual per-page CSS coverage** ("minimal unused CSS") — no live coverage-profiling tool available in this environment.
- **Exact image pixel dimensions vs. CSS display size** for WebP files — no image-dimension tool (`cwebp`, ImageMagick, Pillow) was available; file-size spot checks show no red flags, but couldn't be measured precisely.
- **The `:focus-within` keyboard-dropdown fix** on a real browser/device, per the note above.
